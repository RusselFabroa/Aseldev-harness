# Agent Note: 插件发现接受官方作用域

Status: implemented

[English](2026-10-21-plugin-market-discovery-by-scope.md) | 中文

## 问题

市场搜索只保留已发布 manifest 声明了真值 `dsh` 字段的包。跨本仓库实测，225 个包中有 45 个声明了它，且全部是 bundle（`dsh.bundle`）或浏览器插件（`dsh.client`）。Host 插件 —— 工具、提供方、服务 Definition，包括市场自身的包 —— 都不声明它，因此搜索无法返回任何一个工具或提供方包，市场存在的那个工作流恰好在 harness 赖以构建的能力上以空结果结束。

## 决定

满足任一规则即接受一个候选：名称以官方包作用域 `@deepseek-ai/dsh-` 开头，或它已发布的 manifest 携带真值 `dsh` 字段。两条规则都在提供方已经执行的 manifest 抓取之后判定，因此注册表文本搜索查询、条目字段（`name`、`version`、`description`、`updatedAt`）、注册表相关性排序，以及可配置的注册表基础 URL 都保持原样。

两条规则是 `findPluginManifest` 里的同一个接受判定，而不是两条代码路径：官方包按作用域被发现，第三方包通过在已发布 `package.json` 中声明 `dsh` 选择加入。安装使用同一判定，因此搜索返回的一切都可安装，市场仍然无法按名称安装任意包。

本仓库没有任何 Host 插件被改为声明 `dsh`。发布在官方作用域之下是已发布包的兼容答案，而名称匹配停留在第一方命名空间内，在那里它不会把无关包误判为插件。

### 为什么作用域规则不是 seam 记录拒绝过的名称启发式

[seam 记录](../architecture/2026-10-21-plugin-market-capability-seam.md)曾以*唯一*信号为由拒绝名称前缀匹配，因为把每个该作用域的包都标记为插件的启发式无法表达第三方插件，并且对仅仅共享该前缀的包说了假话。该拒绝依然成立：`dsh` 字段仍是第三方包变得可被发现的唯一方式，作用域规则只是命名了一个本项目控制的命名空间。

## 考虑过的替代方案

**在每个 Host 插件包中声明 `dsh`。** 这是诚实的长期约定，但它会改写约 180 个已发布 manifest，并且没声明该字段就发布的包在下次发版前一直不可见 —— 已发布插件的兼容答案必须来自注册表已经承载的东西。

**注册表侧的插件标记，例如保留的 npm 关键字或专门文档。** npm 关键字是任何包都能抢占的作者自填文本，而没人发布的第二份文档重复了当初使 `dsh` 变得必要的那道缺口；两者还都需要改动提供方才能读取。

**去掉过滤器并返回全部搜索命中。** 那样索引就决定了什么是插件：与查询文本匹配的无关包会被作为可安装项交给模型，而 `plugin_install` 会挂载该名称解析出的任何东西。

## 后果

搜索会返回 Host 插件，这正是市场为之而建的能力。代价是命名空间耦合：`@deepseek-ai/dsh-` 之下的一切都被当作插件，因此将来该作用域里出现非插件包时，它会被搜到并可按名称安装 —— 它会在挂载时失败，且是在用户批准安装之后。第三方发现机制不变，仍取决于作者是否声明 `dsh`，而作用域之外不声明该字段的包依然不可见。

## 测试

`packages/market/market-npm/tests/install.spec.ts` 针对桩注册表钉住全部四种接受结果：无 `dsh` 字段的官方作用域包被返回、带该字段的第三方包被返回、两者皆无的包被丢弃，以及官方作用域包按最新已发布版本安装。`packages/market/tool-market/tests/tool-market.spec.ts` 钉住指明两条规则的空结果文本。
